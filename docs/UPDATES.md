# Releases and updates

The public update endpoint is `https://api.github.com/repos/mochimilk/jellyflower/releases/latest`. GitHub's [latest release API](https://docs.github.com/en/rest/releases/releases#get-the-latest-release) excludes drafts and prereleases. No server, account, API token, or paid hosting is needed on users' computers.

Select the installed version row (`v0.15.0`) to check. Its primary label always shows the running version. Results appear in the menu without notifications. A closed package is idle/current; checking uses a rotating icon; an open package means available. Select an available update to download, verify, quietly install, and relaunch. The spinner continues through `downloading...` and `installing...`. No browser or manual EXE launch is involved. Checks and installation happen only after these explicit clicks. Updating from 0.14.1 or earlier to this first in-app-update release still requires running its installer once.

WinHTTP uses normal TLS certificate validation, system proxy settings, bounded timeouts and read deadlines. Metadata is limited to 1 MiB. Numeric stable versions only are accepted; drafts/previews/downgrades are excluded. An offered installer must be an uploaded asset for the running native architecture at the exact repository/release URL, with an integral size of 1–64 MiB and a valid GitHub `sha256:` asset digest. Missing architecture assets/digests, malformed JSON, rate limits and network errors never launch anything.

Downloads use a unique folder under `%LOCALAPPDATA%\jellyflower\updates`, exclusively create a new file, and follow at most three HTTPS redirects to GitHub's release asset CDN hosts (`release-assets.githubusercontent.com` / `objects.githubusercontent.com`). Other hosts, credentials in URLs, nonstandard ports and HTTP are rejected. Received byte count and Windows BCrypt SHA-256 must match metadata. Partial, oversized, corrupted, cancelled or unverifiable downloads are discarded. The controller verifies again before CreateProcess launches the exact path with `--update`; there is no shell command or browser. Workers own shared result/cancellation state rather than HWND/controller pointers. Exiting while checking/downloading cancels the handoff and leaves the installed version alone. Once setup begins replacement, let it finish.

Setup stages the embedded payload and a copy of the uninstaller into a separate version directory before stopping the old controller. It snapshots the app's startup value, uninstall registration and shortcut, updates them, and checks that the new controller creates its window without immediately exiting. On a handled failure after stopping, it attempts to restore these records and restart the prior controller. This is recovery for ordinary failures, not an atomic transaction against power loss or process termination. Old files remain available; Explorer-pinned helpers are never forcibly unloaded or deleted. In-app setup is silent. Failure before replacement appears as `try again` in the still-running menu; rollback/relaunch reads a persisted update error. Read `%LOCALAPPDATA%\jellyflower\diagnostics.log` for errors. A later launch removes unlocked old download files.

Setup now waits for actual mutex ownership instead of treating `ERROR_ALREADY_EXISTS` as a busy installation. It releases ownership before its completion dialog, so a finished setup window cannot cause false Windows error 170 on later updates. An actively working new installer still excludes another install/uninstall. An old setup version did not take ownership; finish any actively working legacy installer before running this version. Extraction-only validation does not take the install lock or change desktop registration.

For the first release, build with `Build.ps1` and run `Publish.ps1` from normal PowerShell with GitHub CLI signed in as mochimilk. It creates a public jellyflower repository if missing, pushes the source, and publishes the matching local x64 installer and any supplied ZIP/checksum files. It does not change the visibility of an existing private repository or force-push history. Windows Credential Manager credentials are kept in their normal store.

For later releases, change the CMake version and app manifest version together, update docs/RELEASE.md, commit, then push a matching `vMAJOR.MINOR.PATCH` tag. The GitHub Actions workflow builds both architectures and creates a release only after both builds and the x64 update checks pass. Keep asset names stable: `jellyflower-setup-x64.exe` and `jellyflower-setup-ARM64.exe`. Source archives are supplied by GitHub for every release. Checksums identify downloads; they are not a substitute for Authenticode signing. The current binaries are unsigned.

Release automation uses the repository's standard `GITHUB_TOKEN` with contents write permission. No personal token is embedded. GitHub requests disclose the user's IP address and app/version user-agent. SHA-256 checks protect the bytes against corruption or substitution relative to the fetched GitHub metadata; they are not independent publisher authentication. Binaries are currently unsigned, so the updater trusts HTTPS and this GitHub repository/account. Code signing remains a future improvement. There is no periodic update check or analytics. Auto theme uses Windows location services only after opt-in; coordinates are kept local and never sent to GitHub or a solar API.
