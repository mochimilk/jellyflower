# Releases and updates

The public update endpoint is `https://api.github.com/repos/mochimilk/jellyflower/releases/latest`. GitHub's [latest release API](https://docs.github.com/en/rest/releases/releases#get-the-latest-release) excludes drafts and prereleases. No server, account, API token, or paid hosting is needed on users' computers.

Open **general**, then select the installed version row (`v0.16.15`) to check. Older versions show the row directly in the main menu. Its primary label always shows the running version. Results appear in the menu without notifications. A closed package is idle/current; checking uses a rotating icon; an open package and `download` label mean an update is ready. Select `download` to download, verify, quietly install, and relaunch. The spinner continues through `downloading...` and `installing...`. No browser or manual EXE launch is involved. Checks and installation happen only after these explicit clicks. In-app updating was introduced in 0.15.0. Updating from 0.14.1 or earlier requires running a newer installer once. Upgrading to 0.16.3 also needs one sign-out/sign-in to load the v13 Explorer helper; in-app setup does not restart Explorer or show a notification.

WinHTTP uses normal TLS certificate validation, system proxy settings, bounded timeouts and read deadlines. Metadata is limited to 1 MiB. Numeric stable versions only are accepted; drafts/previews/downgrades are excluded. An offered installer must be an uploaded asset for the running native architecture at the exact repository/release URL, with an integral size of 1â€“64 MiB and a valid GitHub `sha256:` asset digest. Missing architecture assets/digests, malformed JSON, rate limits and network errors never launch anything.

Downloads use a unique folder under `%LOCALAPPDATA%\jellyflower\updates`, exclusively create a new file, and follow at most three HTTPS redirects to GitHub's release asset CDN hosts (`release-assets.githubusercontent.com` / `objects.githubusercontent.com`). Other hosts, credentials in URLs, nonstandard ports and HTTP are rejected. Received byte count and Windows BCrypt SHA-256 must match metadata. Partial, oversized, corrupted, cancelled or unverifiable downloads are discarded. The controller verifies again before CreateProcess launches the exact path with `--update`; there is no shell command or browser. Workers own shared result/cancellation state rather than HWND/controller pointers. Exiting while checking/downloading cancels the handoff and leaves the installed version alone. Once setup begins replacement, let it finish.

Setup stages the embedded payload and a copy of the uninstaller into a separate version directory before stopping the old controller. It snapshots the app's complete logon-task XML, Run fallback value, uninstall registration and shortcut, updates them, and checks that the new controller creates its window without immediately exiting. On a handled failure after stopping, it attempts to restore these records and restart the prior controller. This is recovery for ordinary failures, not an atomic transaction against power loss or process termination. Old files remain available; Explorer-pinned helpers are never forcibly unloaded or deleted. In-app setup is silent. Failure before replacement appears as `try again` in the still-running menu; rollback/relaunch reads a persisted update error. Read `%LOCALAPPDATA%\jellyflower\diagnostics.log` for errors. A later launch removes unlocked old download files.

Setup now waits for actual mutex ownership instead of treating `ERROR_ALREADY_EXISTS` as a busy installation. It releases ownership before its completion dialog, so a finished setup window cannot cause false Windows error 170 on later updates. An actively working new installer still excludes another install/uninstall. An old setup version did not take ownership; finish any actively working legacy installer before running this version. Extraction-only validation does not take the install lock or change desktop registration.

For the first release, build with `Build.ps1` and run `Publish.ps1` from normal PowerShell with GitHub CLI signed in as mochimilk. It creates a public jellyflower repository if missing, pushes the source, and publishes the matching local x64 installer and any supplied ZIP/checksum files. It does not change the visibility of an existing private repository or force-push history. Windows Credential Manager credentials are kept in their normal store.

For later releases, change the CMake version and app manifest version together, update docs/RELEASE.md, commit, then push a matching `vMAJOR.MINOR.PATCH` tag. The GitHub Actions workflow builds both architectures and creates a release only after both builds and the x64 update checks pass. Keep asset names stable: `jellyflower-setup-x64.exe` and `jellyflower-setup-ARM64.exe`. Source archives are supplied by GitHub for every release. Checksums identify downloads; they are not a substitute for Authenticode signing. The current binaries are unsigned.

Release automation uses the repository's standard `GITHUB_TOKEN` with contents write permission. No personal token is embedded. GitHub requests disclose the user's IP address and app/version user-agent. SHA-256 checks protect the bytes against corruption or substitution relative to the fetched GitHub metadata; they are not independent publisher authentication. Binaries are currently unsigned, so the updater trusts HTTPS and this GitHub repository/account. Code signing remains a future improvement. There is no periodic update check or analytics. Auto theme uses Windows location services only after opt-in; coordinates are kept local and never sent to GitHub or a solar API.

Since 0.16.3 startup uses a no-delay normal-user logon task named `jellyflower-<SID>`. Setup creates/updates the task before updating the Run fallback, never stores a password, and permits running on batteries without a runtime limit. A handled setup failure attempts to restore the prior task XML (including enabled state) or remove a newly created task, alongside the Run/uninstall/shortcut snapshots. An obsolete uninstaller cannot remove a newer executable's startup. Both startup paths are removed on uninstall; Windows may still draw the default taskbar before user-app attachment.

0.16.4 reverts only controller/menu typography to Windows-provided menu metrics. Updating from 0.16.3 takes effect after automatic relaunch; helper v13 and startup are unchanged, so another sign-out or reboot is unnecessary.

0.16.5 moves update and exit into general and adds a separate versioned Start-menu helper. Updating from 0.16.4 applies after relaunch without restarting Explorer or Start. Start helpers are pinned until StartMenuExperienceHost exits, restore styling on owner shutdown, and reconnect to later controllers through their own mapping/epoch. Future incompatible Start helpers must use a new DLL/mapping version; do not change a published pinned implementation in place.

0.16.6 adds the GitHub link and exit divider inside general. Its separate v2 Start helper fixes the stacked tint and waits for v1 restoration before attaching, without forcibly restarting Start. Old pinned helper files can remain until Windows releases them; the installed app uses only the current helper.

0.16.8 adds the native Start search-header styling and live cursor hover previews. Start v3 waits for older Start helpers to restore their properties before connecting; the Explorer helper is unchanged. These changes apply after the updater relaunches jellyflower, without signing out or restarting Explorer/Start. A suspended Start host can defer styling until its UI thread runs again.

0.16.9 also ignores queued cursor hover events after hiding/dismissing the menu, so they cannot restart a temporary preview. This controller-only correction requires no shell restart.

0.16.10 adds cached daily solar transitions with a dedicated event timer, compact Start side spacing and a 20-DIP outer radius. Start v4 waits for earlier Start surface/search adapters to restore before attachment, without restarting the shell.

0.16.12 uses Start v10 for viewport-based columns, Recommended alignment, matched shadow/content corners and the 20-DIP primary search icon. It waits for v4's surface/search/spacing counters, as well as earlier generations, to restore before attaching. Explorer v13 and the updater protocol remain unchanged; no shell restart or sign-out is required.


0.16.13 uses Start/Search v12. It adopts Recommended GridViews created before their parents attach, clears native wrapper and inner-template width constraints, and keeps each tile filling its responsive column. SearchHost's native editable header receives the shared magnifier/divider and borderless styling. Its sandbox receives read/execute permission only on the app-owned helper; state and lifetime handles are duplicated with minimal rights rather than broadening folder or named-mapping permissions. Older Start helpers restore before the new generation attaches. No forced Search launch, shell restart or sign-out is required. A suspended Search UI may apply changes only when it next runs. Explorer v13 and the updater protocol remain unchanged.


0.16.14 uses Start/Search v13. A coalesced native header remeasure runs on initial attachment, header size changes and return to the viewport, preserving scroll position and avoiding periodic layout writes. Search uses matching 20-DIP frame corners (19 DIP on the inset background) and 12 DIP before its native results region. Older Start/Search helpers restore before the new generation attaches. Explorer v13 and the updater protocol are unchanged.

Cursor hover previews now use a cached local menu pointer rather than loading/replacing the 17 system cursor roles. Only clicking applies the scheme. Menu redraws are limited to changed rows and DirectWrite layouts are reused; unused unlock artwork and spinner initialization are skipped when opening the main menu. These controller changes require no shell restart.


0.16.15 uses Explorer v14 for the lighter light-mode taskbar recipe (white tint and brightness 0.48; legacy alpha 122/255). Updating from a previous Explorer helper needs one sign-out/sign-in or Windows restart; the existing incompatible-helper guard leaves the taskbar native until then. Setup does not restart Explorer or sign the user out. Fresh installs use v14 immediately. Start/Search v13, dark acrylic, pure/off and menu recipes are unchanged.
