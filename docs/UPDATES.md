# Releases and updates

The public update endpoint is `https://api.github.com/repos/mochimilk/jellyflower/releases/latest`. GitHub's [latest release API](https://docs.github.com/en/rest/releases/releases#get-the-latest-release) excludes drafts and prereleases. No server, account, API token, or paid hosting is needed on users' computers.

Open **general**, then select the installed version row (`v0.17.2`) to check. Older versions show the row directly in the main menu. Its primary label always shows the running version. Results appear in the menu without notifications. A closed package is idle/current; checking uses a rotating icon; an open package and `download` label mean an update is ready. Select `download` to download, verify, quietly install, and relaunch. The spinner continues through `downloading...` and `installing...`. No browser or manual EXE launch is involved. Checks and installation happen only after these explicit clicks. In-app updating was introduced in 0.15.0. Updating from 0.14.1 or earlier requires running a newer installer once. Upgrading to 0.16.3 also needs one sign-out/sign-in to load the v13 Explorer helper; in-app setup does not restart Explorer or show a notification.

WinHTTP uses normal TLS certificate validation, system proxy settings, bounded timeouts and read deadlines. Metadata is limited to 1 MiB. Numeric stable versions only are accepted; drafts/previews/downgrades are excluded. An offered installer must be an uploaded asset for the running native architecture at the exact repository/release URL, with an integral size of 1Ã¢â‚¬â€œ64 MiB and a valid GitHub `sha256:` asset digest. Missing architecture assets/digests, malformed JSON, rate limits and network errors never launch anything.

Downloads use a unique folder under `%LOCALAPPDATA%\jellyflower\updates`, exclusively create a new file, and follow at most three HTTPS redirects to GitHub's release asset CDN hosts (`release-assets.githubusercontent.com` / `objects.githubusercontent.com`). Other hosts, credentials in URLs, nonstandard ports and HTTP are rejected. Received byte count and Windows BCrypt SHA-256 must match metadata. Partial, oversized, corrupted, cancelled or unverifiable downloads are discarded. The controller verifies again before CreateProcess launches the exact path with `--update`; there is no shell command or browser. Workers own shared result/cancellation state rather than HWND/controller pointers. Exiting while checking/downloading cancels the handoff and leaves the installed version alone. Once setup begins replacement, let it finish.

Setup stages the embedded payload and a copy of the uninstaller into a separate version directory before stopping the old controller. It snapshots the app's complete logon-task XML, Run fallback value, uninstall registration and shortcut, updates them, and checks that the new controller creates its window without immediately exiting. On a handled failure after stopping, it attempts to restore these records and restart the prior controller. This is recovery for ordinary failures, not an atomic transaction against power loss or process termination. Old files remain available; Explorer-pinned helpers are never forcibly unloaded or deleted. In-app setup is silent. Failure before replacement appears as `try again` in the still-running menu; rollback/relaunch reads a persisted update error. Read `%LOCALAPPDATA%\jellyflower\diagnostics.log` for errors. A later launch removes unlocked old download files.

Setup now waits for actual mutex ownership instead of treating `ERROR_ALREADY_EXISTS` as a busy installation. It releases ownership before its completion dialog, so a finished setup window cannot cause false Windows error 170 on later updates. An actively working new installer still excludes another install/uninstall. An old setup version did not take ownership; finish any actively working legacy installer before running this version. Extraction-only validation does not take the install lock or change desktop registration.

To release, change the CMake version and app manifest version together, update docs/RELEASE.md, commit, then push a matching `vMAJOR.MINOR.PATCH` tag. The GitHub Actions workflow builds both architectures and creates a release only after both builds and the x64 update checks pass. Keep asset names stable: `jellyflower-setup-x64.exe` and `jellyflower-setup-ARM64.exe`. Source archives are supplied by GitHub for every release. Checksums identify downloads; they are not a substitute for Authenticode signing. The current binaries are unsigned.

Release automation uses the repository's standard `GITHUB_TOKEN` with contents write permission. No personal token is embedded. GitHub requests disclose the user's IP address and app/version user-agent. SHA-256 checks protect the bytes against corruption or substitution relative to the fetched GitHub metadata; they are not independent publisher authentication. Binaries are currently unsigned, so the updater trusts HTTPS and this GitHub repository/account. Code signing remains a future improvement. There is no periodic update check or analytics. Auto theme uses Windows location services only after opt-in; coordinates are kept local and never sent to GitHub or a solar API.

Since 0.16.3 startup uses a no-delay normal-user logon task named `jellyflower-<SID>`. Setup creates/updates the task before updating the Run fallback, never stores a password, and permits running on batteries without a runtime limit. A handled setup failure attempts to restore the prior task XML (including enabled state) or remove a newly created task, alongside the Run/uninstall/shortcut snapshots. An obsolete uninstaller cannot remove a newer executable's startup. Both startup paths are removed on uninstall; Windows may still draw the default taskbar before user-app attachment.

0.16.4 reverts only controller/menu typography to Windows-provided menu metrics. Updating from 0.16.3 takes effect after automatic relaunch; helper v13 and startup are unchanged, so another sign-out or reboot is unnecessary.

0.16.5 moves update and exit into general and adds a separate versioned Start-menu helper. Updating from 0.16.4 applies after relaunch without restarting Explorer or Start. Start helpers are pinned until StartMenuExperienceHost exits, restore styling on owner shutdown, and reconnect to later controllers through their own mapping/epoch. Future incompatible Start helpers must use a new DLL/mapping version; do not change a published pinned implementation in place.

0.16.6 adds the GitHub link and exit divider inside general. Its separate v2 Start helper fixes the stacked tint and waits for v1 restoration before attaching, without forcibly restarting Start. Old pinned helper files can remain until Windows releases them; the installed app uses only the current helper.

0.16.8 adds the native Start search-header styling and live cursor hover previews. Start v3 waits for older Start helpers to restore their properties before connecting; the Explorer helper is unchanged. These changes apply after the updater relaunches jellyflower, without signing out or restarting Explorer/Start. A suspended Start host can defer styling until its UI thread runs again.

0.16.9 also ignores queued cursor hover events after hiding/dismissing the menu, so they cannot restart a temporary preview. This controller-only correction requires no shell restart.

0.16.10 adds cached daily solar transitions with a dedicated event timer, compact Start side spacing and a 20-DIP outer radius. Start v4 waits for earlier Start surface/search adapters to restore before attachment, without restarting the shell.

0.16.12 uses Start v10 for viewport-based columns, Recommended alignment, matched shadow/content corners and the 20-DIP primary search icon. It waits for v4's surface/search/spacing counters, as well as earlier generations, to restore before attaching. Explorer v13 and the updater protocol remain unchanged; no shell restart or sign-out is required.


0.16.13 uses Start/Search v12. It adopts Recommended GridViews created before their parents attach, clears native wrapper and inner-template width constraints, and keeps each tile filling its responsive column. SearchHost's native editable header receives the shared magnifier/divider and borderless styling. Its sandbox receives read/execute permission only on the app-owned helper; state and lifetime handles are duplicated with minimal rights rather than broadening folder or named-mapping permissions. Older Start helpers restore before the new generation attaches. No forced Search launch, shell restart or sign-out is required. A suspended Search UI may apply changes only when it next runs. Explorer v13 and the updater protocol remain unchanged.


0.16.14 uses Start/Search v13. A coalesced native header remeasure runs on initial attachment, header size changes and return to the viewport, preserving scroll position and avoiding periodic layout writes. Search uses matching 20-DIP frame corners (19 DIP on the inset background) and 12 DIP before its native results region. Older Start/Search helpers restore before the new generation attaches. Explorer v13 and the updater protocol are unchanged.

Cursor hover previews now use a cached local menu pointer rather than loading/replacing the 17 system cursor roles. Only clicking applies the scheme. Menu redraws are limited to changed rows and DirectWrite layouts are reused; unused unlock artwork and spinner initialization are skipped when opening the main menu. These controller changes require no shell restart.


0.16.15 uses Explorer v14 for the lighter light-mode taskbar recipe (white tint and brightness 0.48; legacy alpha 122/255). Updating from a previous Explorer helper needs one sign-out/sign-in or Windows restart; the existing incompatible-helper guard leaves the taskbar native until then. Setup does not restart Explorer or sign the user out. Fresh installs use v14 immediately. Start/Search v13, dark acrylic, pure/off and menu recipes are unchanged.

0.16.16 embeds the optional light/dark jellyflower wallpapers. The setting and per-monitor recovery images live in the account data folder, independent of installed version folders. An in-app update keeps the preference and original backup. Explorer v14 and Start/Search v13 are unchanged; users already on 0.16.15 need no extra sign-out.

0.16.17 uses Explorer v15 for the lighter light-mode taskbar recipe (white tint and brightness 0.30; legacy alpha 77/255). Updating from a previous loaded Explorer helper requires one sign-out/sign-in or restart. The app preserves the existing incompatible-helper guard and never restarts Explorer automatically. Start/Search v13 and the wallpaper setting/recovery data remain unchanged.

0.16.18 uses Start/Search v14 for the compact account badge and theme-aware heart placeholder. 0.16.19 uses Start/Search v15 for native-side/mirrored-vertical account padding, tooltip suppression and the PC-name placeholder. 0.16.20 uses Start/Search v16 for the vertical-only two-DIP badge reduction, explicit vertical content centering and capitalized Search placeholder. It waits for older helpers through v15 to restore. Explorer stays v15; users already on 0.16.17 or newer need no additional sign-out.

0.16.21 uses Start/Search v17 for another two-DIP vertical-only badge reduction (eight-DIP visible vertical gaps on the inspected native template). Older helpers through v16 restore before connection. Explorer remains v15; updating from 0.16.17 or newer needs no additional sign-out.

0.16.22 uses Start/Search v18 for responsive square pinned hover targets, 12-DIP pinned/action corners and a centered footer with 16 extra DIP of height. Older helpers through v17 restore before connection. Explorer remains v15; updating from 0.16.17 or newer needs no additional sign-out.

The 0.16.22 Start/Search v18 mapping also carries three immutable account-name greetings and an atomic local-clock period selector. No extra timer or typed-query change is introduced.

0.16.23 uses Start/Search v19 for the square auto-height power control and corrected first-name greetings. The controller reads the current Windows given-name field once in the background; sign-in IDs are no longer a fallback. New helper/mapping identities avoid v18's stale immutable greeting. Older helpers through v18 restore before connection. Explorer remains v15; no additional sign-out is needed from 0.16.17 or newer.

0.16.24 keeps Start/Search v19, Explorer v15 and the v1 wallpaper recovery format. The controller replaces disconnected wallpaper COM proxies, ignores untouched detached-display assignments, and uses a guarded Windows-reported current-image copy when the original cannot be read. Existing recovery records remain usable, including queryable older detached assignments already using jellyflower images. New controller-only diagnostic queries do not change either injected helper protocol. No additional sign-out is needed from 0.16.17 or newer.

0.17.0 reorganizes the controller's popup menu into taskbar and wallpaper branches. Acrylic/date preferences and wallpaper v1 backups migrate unchanged. WallpaperTheme is a separate DWORD (0 system, 1 auto), with isolated WallpaperAutoTheme/WallpaperThemeLocation records; existing AutoTheme/ThemeLocation continue to control only Windows color mode. Native Windows auto-hide remains owned by Windows, not an app startup override. Start/Search v19 and Explorer v15 remain compatible; no extra sign-out is required from 0.16.17 onward.

0.17.1 changes only controller-side location ownership. Both auto scopes use bounded one-shot requests with cancellation, retaining no locator/status listener between readings. Existing rounded caches, solar deadlines, wallpaper v1 recovery and the 0.17.0 menus remain compatible. Start/Search stays v19 and Explorer stays v15, with no added sign-out from 0.16.17 onward. Windows location permission/global services remain user-managed.

0.17.2 fixes controller-side wallpaper capture/recovery and records path-free error stages. The existing wallpaper v1 state and original backups remain compatible; Start/Search v19 and Explorer v15 remain unchanged. It applies after the updater relaunch without an additional sign-out. The other laptop's missing-image path is still unconfirmed; an unreadable source without a safe current-picture copy remains an error.

0.20.0 adds the jellyflower-only tray and ships Explorer helper v19 (`jellyflower-bridge-v19.dll`, mapping `AcrylicTaskbar.Bridge.v19`, notify class `AcrylicTaskbar.BridgeNotify.v19`, magic `0x41544243`). `SharedState` appends `trayOptions`, `trayHidden`, `trayFlower` and `trayResult`; the first 17 fields are unchanged. A normally stopped v18 (0.19.0) helper is asked to restore synchronously and is retired once its counters read zero; a live or unknown older helper still blocks attachment. Start/Search stays v20: its code and `StartState` are unchanged, and the strings appended to the shared text table are never read by it. Windows may keep v18's diagnostics connection, so the taskbar styling can need one sign-out after the in-app update. The new preference is the `TrayOnly` DWORD under `HKCU\Software\jellyflower` (0 or missing: all icons). `--diagnose` adds `trayOnlyJellyflower`, `hiddenTrayParts`, `trayJellyflowerIcons` and `trayLastResult`.

0.21.0 adds the symmetric touch keyboard and Start's narrow layout, and ships Start/Search helper v21 (`jellyflower-start-v21.dll`, mapping `jellyflower.Start.v21.<pid>`, notify class `jellyflower.StartNotify.v21`, magic `0x4a465315`, init marker `JFStart21`, new TAP class GUID). `StartState` appends `keyboard`, `keyboards` and `keyboardField` (0 unknown, 1 empty, 2 text) after the greetings; its first 11 fields are unchanged and v20 joins the retired list, so a normally stopped v20 (0.20.0) restores Start and Search before v21 attaches, without a sign-out. The same helper attaches to the touch keyboard's `TextInputHost.exe` (medium integrity, so no file grant as for Search) only after the user chooses `symmetric`, and stays pinned there until TextInputHost exits; turning the layout off restores Windows' layout in place. The narrow Start layout (see docs/START_MENU.md) adds no `StartState` fields, preference or diagnostics. Explorer stays v19: the strings and `--diagnose` queries appended to its shared headers are never read by it. The preference is the `KeyboardLayout` DWORD under `HKCU\Software\jellyflower` (0 or missing: system). The controller watches the focused field through UI Automation only while the symmetric layout is on. `--diagnose` adds `keyboardLayout`, `keyboardAttached`, `keyboardSymmetricGrids`, `keyboardLastResult` and `keyboardField` ("off" when the layout is off).

A development v21 helper already pinned in Start, Search or TextInputHost keeps its older code until that process restarts. It also keeps its smaller mapping section: a newer controller still maps it while `sizeof(StartState)` stays within the same page-rounded size (currently under 8192 bytes); grow it past that within v21 and the host stays stock until it restarts.

0.22.0 adds the floating dock and ships Explorer helper v20 (`jellyflower-bridge-v20.dll`, mapping `AcrylicTaskbar.Bridge.v20.<pid>`, notify class `AcrylicTaskbar.BridgeNotify.v20`, magic `0x41544244`, new TAP class GUID). `SharedState` appends `dockOptions`, `dockCount`, `dockRegions`, `dockResult`, `barHeight`, `minSizeSlot`, `minSizeFunction`, `barHeightShown` and `barHeightResult`, and `trayOptions` gains bit 1 (the menu is in the status bar); the first 21 fields are unchanged. v19 joins `OlderBridgePresent`: a normally stopped 0.20.0 or 0.21.0 helper is asked to restore and is retired once its counters, `trayHidden` included, read zero, so no sign-out is needed unless Windows keeps the old diagnostics connection. The preference is the `Dock` DWORD under `HKCU\Software\jellyflower` (0 or missing: off). Once the dock is on, the controller caches Taskbar.dll's `TrayUI::GetMinSize` slot there as `MinSizeSlot` (REG_SZ) after a one-time download of Taskbar.dll's public symbols from Microsoft; a Windows update that changes Taskbar.dll triggers a new lookup, and until it succeeds the dock floats at the stock 48-DIP height. `--diagnose` adds `floatingDock`, `dockTaskbars`, `clickThroughTaskbars`, `dockLastResult`, `taskbarHeight` and `taskbarHeightResult`. On exit the controller now removes the compact app bars, then restores the Explorer helper, then removes its tray icon.

0.22.0 also adds compact displays (narrower than Start's 666 DIP). The controller registers four app bars per compact display and draws the status bar; this is controller-only, and Explorer, Start and Search helpers need nothing new for it. While the status bar shows the menu, the flower is `NIS_HIDDEN` and `trayOptions` bit 1 tells the v20 helper to hide the tray's chevron in `jellyflower` tray mode; a pinned v19 ignores the bit. The preference is the `StatusBar` DWORD under `HKCU\Software\jellyflower` (missing: on; 0: off, margins kept). App bars disappear with the controller's window, so a killed controller leaves the stock work area. `--diagnose` adds `compactDisplays`, `statusBar` and `compactLastResult`.

0.23.0 draws jellyflower's menus in fluted glass. It is controller-only: the Explorer helper stays v20 and the Start/Search helper v21, so updating from 0.22.0 needs no sign-out. The glass uses Windows.UI.Composition in the controller (a dispatcher queue, a compositor and a Direct3D 11 device on the menu's thread, created when the first menu opens and kept for the process). While energy saver is on, or if the glass can't be drawn, menus fall back to the accent acrylic of 0.22.0. There is no new preference. `--diagnose` adds `menuGlassResult`, and the `Query` enum appends `MenuGlassResultQuery` at its end.

0.24.0 adds the `fluted` taskbar style and makes it the default, and ships Explorer helper v21 (`jellyflower-bridge-v21.dll`, mapping `AcrylicTaskbar.Bridge.v21.<pid>`, notify class `AcrylicTaskbar.BridgeNotify.v21`, magic `0x41544245`, new TAP class GUID). `SharedState` appends `flutedCount`, `flutedResult`, `glassSequence`, `glassSlots[4][6]`, `glassShown` and `glassResult`; the first 30 fields are unchanged. v20 joins `OlderBridgePresent`: a normally stopped 0.22.0 or 0.23.0 helper is asked to restore and is retired once its counters, the dock's `dockCount`, `dockRegions` and `barHeightShown` included, read zero, so no sign-out is needed unless Windows keeps the old diagnostics connection. The glass itself is drawn by the controller in its own windows (`jellyflower.FlutedGlass`), which the helper places through the glass slots and the controller's window message `WM_APP + 110`. The taskbar style is now saved as the `Acrylic` DWORD under `HKCU\Software\jellyflower` (0 off, 1 system, 2 pure, 3 fluted; missing means fluted); before 0.24.0 it wasn't saved and every start began at `system`, so an update starts at `fluted`. `--diagnose` adds `flutedTaskbars` and `flutedLastResult`, and `acrylicMode` can read `fluted`.

0.24.0 also adds the top bar and the system tray menu. Both are controller-only: they need nothing from Explorer helper v21 and leave the Start/Search helper at v21, so they add no sign-out. taskbar's date, tray and status bar rows move into a new taskbar > system tray submenu, with tray renamed show; their preferences (`TrayOnly`, `StatusBar` and the clock's date) are unchanged. Its new position row saves `TopBar` (off by default) under `HKCU\Software\jellyflower`. `--diagnose` adds `topBar` and `topBarDisplays`, and the `Query` enum appends `TopBarQuery` and `TopBarDisplaysQuery` after `FlutedResultQuery`. Tray commands 22 and 23 are taken; 21 stays reserved for autocorrect. The text table changes the `Tray` string in place and appends six strings, which changes the Start/Search helper's bytes but not what it does.
