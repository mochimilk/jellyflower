# Battery saver and acrylic: findings

Inspected 2026-10-08. Upstream: [TranslucentTB](https://github.com/TranslucentTB/TranslucentTB), release-branch commit [`d4636e439865df0a1a1419db408e055740ce5c74`](https://github.com/TranslucentTB/TranslucentTB/commit/d4636e439865df0a1a1419db408e055740ce5c74), dated 2026-08-31. Findings describe that source snapshot, not an unverified installed version.

## What the upstream application does

The taskbar worker registers for power-saving changes. `OnPowerBroadcast` updates `m_PowerSaver` and refreshes appearance. `GetConfig` selects a battery-saver appearance only when `BatterySaverAppearance.Enabled` is true. In the inspected configuration the override starts **disabled**; when enabled, its default appearance is opaque. The reviewed power-handling path changes appearance; it does not terminate the app. Thus an apparent visual shutdown is not sufficient evidence that the process exited. Sources: [taskbarattributeworker.cpp](https://github.com/TranslucentTB/TranslucentTB/blob/d4636e439865df0a1a1419db408e055740ce5c74/TranslucentTB/taskbar/taskbarattributeworker.cpp), [config.hpp](https://github.com/TranslucentTB/TranslucentTB/blob/d4636e439865df0a1a1419db408e055740ce5c74/Common/config/config.hpp).

Legacy taskbars receive an acrylic accent using `SetWindowCompositionAttribute`. For modern Windows 11, upstream uses an Explorer TAP service to replace the taskbar background with `Windows.UI.Xaml.Media.AcrylicBrush`. Its `Backdrop` source avoids the inactive-window behavior of `HostBackdrop`. This fixes deactivation behavior, not every acrylic fallback condition. Sources: [taskbar worker](https://github.com/TranslucentTB/TranslucentTB/blob/d4636e439865df0a1a1419db408e055740ce5c74/TranslucentTB/taskbar/taskbarattributeworker.cpp), [taskbar appearance service](https://github.com/TranslucentTB/TranslucentTB/blob/d4636e439865df0a1a1419db408e055740ce5c74/ExplorerTAP/taskbarappearanceservice.cpp).

## What Windows can do

Microsoft documents that acrylic becomes solid under battery saver, with transparency effects disabled, in high contrast, or on hardware that cannot render the material. This is system/material policy; it does not require the taskbar utility to exit. `AlwaysUseFallback = false` removes an application's forced fallback, but it is not an override for the system's fallback conditions. Sources: [Acrylic material](https://learn.microsoft.com/en-us/windows/apps/design/style/acrylic), [Windows.UI.Xaml AcrylicBrush.AlwaysUseFallback](https://learn.microsoft.com/en-us/uwp/api/windows.ui.xaml.media.acrylicbrush.alwaysusefallback?view=winrt-26100).

Those documented XAML rules directly matter to the modern backend. The undocumented legacy accent is a different path: its exact battery-saver behavior must be tested per Windows build and driver. We cannot infer that continuously setting an accent will defeat a compositor or shell policy.

The evidence supports two independent causes for a changed taskbar: an optional TranslucentTB appearance override, and Windows' own acrylic fallback. On the inspected default configuration, the disabled override makes Windows fallback a plausible explanation for a modern taskbar losing blur. That is an inference, not a diagnosis of the user's laptop. A third possibility, actual process exit/crash, requires observing the PID or crash evidence. The cached earlier conversation did not supply such measurements.

## What this utility changes

AcrylicTaskbar runs as an unpackaged native desktop process with no battery-saver stop/exit branch. Power notifications preserve the selected taskbar mode; startup defaults to acrylic on, and the tray toggle can select the default taskbar for the current run. Startup uses the current user's Run entry; there is no Task Scheduler job with battery-related start/stop conditions. It has no battery-saver appearance override and no UI framework for settings.

For the modern taskbar it still uses the system acrylic brush. Replacing that brush repeatedly cannot guarantee rendering while the system suppresses the effect. The legacy adapter also makes no guarantee about an undocumented rendering path. The implementation does not disable battery saver, change global transparency settings, alter DWM, hook acrylic policy functions, or substitute a custom screenshot/blur renderer.

Guaranteeing visible acrylic during battery saver would require separate investigation into a custom composition effect or shell-specific policy interception. Those are larger, less stable approaches and are not implemented here. The current project's concrete guarantee is in its control flow: battery-saver events do not voluntarily stop the controller or select another appearance. Native runtime validation remains necessary.

## Source and attachment limits

The modern helper borrows upstream's visual-tree targeting and acrylic technique, but omits its general appearance service, RPC stubs, Detours dependency, menus, packaged deployment, state rules, and updater. It bootstraps through a taskbar-thread `WH_CALLWNDPROC` hook, then attaches with `InitializeXamlDiagnosticsEx`, which loads an `IObjectWithSite` TAP DLL in Explorer. Microsoft documents [that diagnostic entry point](https://learn.microsoft.com/en-us/windows/win32/api/xamlom/nf-xamlom-initializexamldiagnosticsex); applying it to internal taskbar elements remains a shell-dependent customization.

The bridge is pinned for Explorer's lifetime so UI callbacks cannot point into unloaded code. UI-thread timers restore stock fills if the controller dies. A failed diagnostic attachment is reported; startup discovery keeps retrying with bounded attempts and delays. Slow/hung shell APIs can still delay attachment. Multiple diagnostic customizers may conflict. Successful attachment, a nonzero applied count, and `S_OK` describe requests and liveness, not GPU output.

On the user's Windows build 26200 desktop, the first session stayed at state 1 with no applied backgrounds and saver off. Closing TranslucentTB alone did not produce acrylic. Restarting Explorer allowed the same AcrylicTaskbar controller to reach state 2, apply one background, and report no error on 2026-10-09. The user then confirmed the original build looked frosted. This establishes attachment recovery and visible acrylic on that session with saver off. It does not establish the exact cause of the initial stall or test battery saver. See [the validation record](VALIDATION.md).

## Intermittent interaction resets, 2026-10-10

The user's normal-desktop diagnostics.log showed the same running controller repeatedly switching Backend=2 (modern XAML) to Backend=3 (unsupported) and back. For example, PID 42956 started at 11:15:32; transitions occurred at 11:18:07/11:18:12 and 11:18:47/11:18:52, without intervening controller stop/start entries. The pre-0.11 controller classified modern Windows only when its descendant XAML island count was exactly one. Any other count selected unsupported and called ReleaseBridge, publishing running=0 and restoring the background, border, and clock. A later refresh could reattach. This is an application-driven restoration path, separate from Windows' material fallback or a process crash. The old log did not record island counts, so the specific transient count/trigger is inferred from that code path.

Version 0.11 accepts one or more islands for initial modern discovery. Once owned, the same live Explorer process retains the bridge through changing/missing HWNDs and island counts. The retained process handle prevents PID reuse from masquerading as the old owner. Actual process replacement/death still releases/reconnects, and exit still publishes lifetime zero. The XAML watcher handles recognized replacement controls, rather than using global discovery counts to decide their lifetime. New island/retention diagnostics make the mechanism observable. This fixes the identified reset path; it does not establish that every possible shell/compositor flash is eliminated.


## System tint over black wallpaper, 2026-10-10

The user reported unreadable taskbar text in light mode over black wallpaper, and confirmed the selected acrylic mode was system. The previous light recipe requested white TintOpacity 0.65 but explicitly set TintLuminosityOpacity to zero. A white color tint is not equivalent to a white alpha overlay: the acrylic effect blends color and brightness separately. Zero luminosity allows the backdrop's brightness to dominate. This code path is consistent with the reported black result; no trace or GPU capture from that computer was available to prove it was the sole cause.

Microsoft documents TintLuminosityOpacity as the brightness layer between tint and backdrop. Its material implementation separates the luminosity and color blends; an explicit luminosity value uses the tint's RGB and that opacity. See [AcrylicBrush.TintLuminosityOpacity](https://learn.microsoft.com/en-us/uwp/api/windows.ui.xaml.media.acrylicbrush.tintluminosityopacity?view=winrt-26100) and [Microsoft's AcrylicBrush implementation](https://github.com/microsoft/microsoft-ui-xaml/blob/main/controls/dev/Materials/Acrylic/AcrylicBrush.cpp). The latter is implementation evidence, not a guarantee of identical internals on every installed Windows version.

Version 0.14.1 sets explicit luminosity 0.85 in both themes, retaining white tint opacity 0.65 and neutral #202020 tint opacity 0.40. Pure still requests zero color/luminosity tint. Legacy accent alpha is 217/255 for both colors, because that backend uses an alpha overlay. The native test verifies production setters on real XAML brushes and a black/white contrast model; actual shell material rendering remains a desktop test. The new v9 helper rejects v1–v8 mappings, preventing a new controller from silently reusing old pinned brush code. Upgraders need one Explorer restart or sign-out/sign-in.

## Installer error 170 and menu rendering in 0.15.0

The old setup called CreateMutex with initial ownership FALSE, rejected any ERROR_ALREADY_EXISTS result, and retained its handle during the completion dialog. An existing mutex object does not mean an operation owns it: see [CreateMutexW](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-createmutexw). A still-open finished installer therefore caused error 170 without an active installation. The native regression reproduces the existing-but-unowned case, verifies real exclusion between installing threads, and verifies release-before-dialog and abandoned-lock recovery. New setup acquires/releases actual ownership. Old installers did not use ownership; finish a genuinely active legacy install before updating.

Menu material now uses the same native SetWindowCompositionAttribute accent acrylic family as the legacy taskbar, with explicit translucent light/dark tints. This API is undocumented, so compositor policy or future Windows changes can still affect it. High contrast/transparency-off chooses a solid surface. The actual root menu was captured over independently repainted red/blue test windows on build 26200: background RGB changed in both themes. This is stronger evidence of live transparency than accepting a DWM attribute. It is not a guarantee of GPU blur/fallback on every computer.

The font face/size/weight remains 10pt regular Segoe UI. Version 0.14.1 changed ClearType to grayscale smoothing for transparent text. Re-testing ClearType revealed hollow/fringed text on glass. Version 0.15.0 uses one neutral grayscale coverage mask in both themes, rather than color-dependent text coverage that could make light text look heavier. One parent foreground surface avoids independently painted child alpha; real button HWNDs retain accessibility/input. GDI operations are flushed before releasing their DIB storage to prevent intermittent incomplete foreground frames. Offscreen and actual compositor captures verify the final drawing path.

## Sunrise/sunset feasibility and implementation

Microsoft documents [location consent for unpackaged Windows apps](https://learn.microsoft.com/en-us/windows/apps/develop/maps-and-location/get-location): no package capability manifest is required, but RequestAccessAsync must run on the foreground UI thread. Microsoft's [PowerToys Light Switch](https://learn.microsoft.com/en-us/windows/powertoys/light-switch) demonstrates this scheduling model. Jellyflower requests consent only when selecting auto, uses city-level accuracy, stores coordinates in its account-local settings, and refreshes the approved location daily. Denied/revoked access stops scheduling; a temporary refresh failure can retain a previously approved location. Startup revalidates without explicitly requesting consent.

Daylight uses the [NOAA fractional-year equation of time, declination and solar zenith](https://gml.noaa.gov/grad/solcalc/solareqns.PDF), with the 90.833-degree sunrise threshold. Computing from UTC avoids DST/date-line conversion errors and naturally represents polar day/night. This is approximate solar timing, not a local weather/horizon model. The real Windows consent/provider and travel/sleep behavior remain normal-desktop acceptance tests; development checks did not read the user's location or alter their theme.


## Windows 11 menu styling and connected network icon (0.16.0)

Microsoft's [Windows typography](https://learn.microsoft.com/en-us/windows/apps/design/signature-experiences/typography) specifies Segoe UI Variable and 14/20 effective-pixel body text. GDI enumerates the installed optical Text face before selecting it, instead of silently asking for a nonexistent generic variable family. The renderer keeps regular weight and grayscale coverage because the foreground is composed onto transparent ARGB pixels; ClearType assumes an opaque subpixel background.

Microsoft's [Windows motion guidance](https://learn.microsoft.com/en-us/windows/apps/design/signature-experiences/motion) says taskbar flyouts slide up and lists Direct Entrance cubic-bezier(0,0,0,1), with 167/250/333-ms durations. Jellyflower uses 250 ms and a 32-DIP upward travel, analytically inverting x=t^3. No public source found establishes the exact current taskbar flyout's private curve, distance, or duration. Work-area inset is a 12-DIP visual target, not a claimed public shell geometry contract. Root-only nonblocking position updates preserve live acrylic and input; interaction settles the animation before changing settings or opening a submenu. Windows animation-off/high-contrast preferences bypass it.

The connected-network adapter checks the first native Quick Settings slot and a named InnerTextBlock. Its conservative whitelist comes from Microsoft's [Segoe Fluent Icons list](https://learn.microsoft.com/en-us/windows/apps/design/iconography/segoe-fluent-icons-font). Only regular Wi-Fi signal/Ethernet/connected glyphs are covered; globe, errors, warnings, connecting animations, and unknown codes are not replaced. A centered vector overlay inherits the actual glyph's Foreground binding. The original text/status/accessibility and button remain; only opacity is temporarily changed, with the original local value/binding restored on disconnect, exit, or failure. v10 isolates this new Explorer implementation from pinned v9 helpers. Real Explorer builds/network transitions remain acceptance checks.


## Network replacement correction and typography (0.16.1)

The 0.16.0 fixture modeled only two nested grids under IconView and tested generic Wi-Fi glyphs. This release incorrectly assumed an extra ContentPresenter before ContentGrid/TextIconContent; the 0.16.2 correction below documents the direct layout. Windows 11 uses MobWifi (EC3C-EC3F) or SysWifi (F8C3-F8C6) glyphs; Ethernet can use TVMonitor E7F4. This explains why the helper could attach successfully without replacing the network icon. The shell template and taskbar-specific glyph identities were checked against [m417z's taskbar tray system icon implementation](https://github.com/ramensoftware/windhawk-mods/blob/main/mods/taskbar-tray-system-icon-tweaks.wh.cpp), a primary implementation source. The updated fixture includes those layers and codes. The selector validates the ControlCenterButton ancestor and named glyph template, without assuming first-slot order. F384 and F8CC offline glyphs, airplane, warnings, connecting, and unknown values are never overlaid; the native text, accessibility, click and tooltip remain.

The user's requested menu typeface is now explicit Segoe UI Regular at 14 effective pixels, replacing Segoe UI Variable Text; normal weight 400 is resolved and checked by GDI. Taskbar system tint and brightness opacity are reduced in both themes (0.58/0.34 tint, 0.72 luminosity). Pure and opaque accessibility/compositor fallbacks are unchanged. v11 rejects older pinned helpers, so one Explorer reload/sign-out is necessary after an upgrade. Real shell appearance and physical network changes remain desktop acceptance checks; a passing fixture does not establish that the user's Explorer tree matched.

Diagnostics add networkGlyphCode: the last code point from a matched network template, as a decimal number, or zero for no match. With multiple monitors it is a recent sample, not per-monitor inventory. It does not contain Wi-Fi names, addresses, or tooltip text. Interpret it only when responsive is true and the current helper is attached.


## Direct network layout and system font selection (0.16.2)

The 0.16.1 selector and fixture both mistakenly required IconView > ContainerGrid > ContentPresenter > ContentGrid. This was an incorrect transfer of a wrapper used by other tray templates. In [m417z's ApplyControlCenterButtonIconStyle](https://github.com/ramensoftware/windhawk-mods/blob/main/mods/taskbar-tray-system-icon-tweaks.wh.cpp), the network path starts IconView > ContainerGrid > ContentGrid directly. The fix tries this direct path first, with the named presenter as an optional alternative. A fixture using the direct path failed on the previous production selector before the fix; both direct and wrapped fixtures are exercised afterward. The rest of the glyph/status validation and reversible overlay is unchanged. This establishes the specific regression without claiming a mock is a captured tree from the user's Explorer.

The complete font comes from Windows' DPI-specific NONCLIENTMETRICS.lfMenuFont via SystemParametersInfoForDpi. Family, size and weight are no longer overridden; the fallback is Windows' DEFAULT_GUI_FONT. Leaving LOGFONT.lfFaceName empty would invoke GDI font mapping, not menu inheritance. Tests inject different menu metrics and a failed-query fallback without changing system settings. On the development PC the configured font is Segoe UI, 12/18/24 pixels at 96/144/192 DPI, weight 400. This is the reported Windows menu font; modern shell components can choose different typography.

The earlier GDI coverage mask also caused a rendering difference independent of the font family. Text now uses DirectWrite natural layout and a Direct2D premultiplied-alpha DC target. Windows' font mapping supplies style/stretch/weight, and font height is converted to an em without added size or weight. The same layout engine measures secondary text and visible ink for icon alignment. Microsoft's [DirectWrite rendering guidance](https://learn.microsoft.com/en-us/windows/win32/directwrite/rendering-directwrite) and [alpha-mode documentation](https://learn.microsoft.com/en-us/windows/win32/direct2d/supported-pixel-formats-and-alpha-modes) support grayscale rendering onto transparent targets; forcing RGB ClearType would assume an opaque background. No manual gamma, contrast or synthetic weight is applied. GDI remains a readable initialization/device-failure fallback. Native alpha/opaque stems/edge coverage, DPI and no-fallback production drawing are tested, but final perceived clarity and exact similarity to the private shell remain visual checks. Helper v12 prevents pinned v11 code from retaining the old network selector.


## 0.16.3: typography resources, network removal and startup

WinUI defines semantic text resources including BodyTextBlockStyle; Microsoft's typography guidance specifies regular Body at 14/20 effective pixels and Segoe UI Variable. These resources belong to XAML applications, not one universal font variable shared by every Windows component. Jellyflower keeps its small native popup and implements that role centrally in menu_style.hpp/menu_text.hpp. DirectWrite uses the installed typographic family, a normal weight axis, 14-DIP em size, 20-DIP line height and automatic optical sizing. Target DPI handles physical scaling; enlarging the em size itself would select the wrong optical proportions. Segoe UI is the compatibility fallback; classic NONCLIENTMETRICS is only for GDI initialization failure. No runtime WinUI package, font download or live shell resource binding is added.

Sources: [Windows typography](https://learn.microsoft.com/en-us/windows/apps/design/signature-experiences/typography), [WinUI TextBlock resources](https://github.com/microsoft/microsoft-ui-xaml/blob/main/controls/dev/CommonStyles/TextBlock_themeresources.xaml), [DirectWrite automatic axes](https://learn.microsoft.com/windows/win32/api/dwrite_3/ne-dwrite_3-dwrite_automatic_font_axes).

The Element 2 replacement is removed entirely from production, assets, build and diagnostics. Earlier network-selector sections are development history; the normal Windows network artwork is now always retained.

Previous startup used only HKCU Run and a five-second shell polling timer. The registration observed on the development account pointed to the installed 0.16.2 executable; there is no measured cold-boot trace proving which component caused the user's delay. The new primary path is a Task Scheduler logon trigger scoped to the current SID, with no trigger delay, normal interactive privileges, no password, no battery/idle/network restriction, and no execution time limit. An updated Run fallback is retained both for reliability and to keep obsolete Run-only uninstallers from removing a newer installation. The existing per-session mutex makes duplicate launches exit. Setup snapshots/restores task XML alongside the registry/shortcut records. Startup applies material before cursor-pack validation/housekeeping; initial/recovery discovery retries every 100 ms for at most 30 seconds. TaskbarCreated also triggers immediate discovery. Maintenance remains five seconds, and the first successful appearance request is logged.

Microsoft documents [interactive-task security contexts](https://learn.microsoft.com/en-us/windows/win32/taskschd/security-contexts-for-running-tasks): a standard user can register an interactive task for their own account without a password. This avoids adding an Explorer Run delay to the primary path; actual Task Scheduler scheduling and shell readiness still vary. Windows can draw its normal taskbar before user login utilities attach. No supported zero-frame guarantee is claimed, and no global StartupDelay registry tweak, administrator service, shell replacement or hiding of the taskbar is used. Test cold startup on AC/battery and actual registration/rollback/uninstall separately from read-only definition checks.

## Wallpaper file and connection failures (0.16.24)

A supplied diagnostic log reports -2147024894 (0x80070002, ERROR_FILE_NOT_FOUND) across fresh app starts and -2147023174 (0x800706ba, RPC_S_SERVER_UNAVAILABLE) after an Explorer restart, until the controller restarts. The old file reader mapped every open failure to file-not-found, so that log does not prove which path was missing or exclude a sharing/permission failure. The controller also retained its IDesktopWallpaper proxy indefinitely. Reproducing a stale proxy with the supplied RPC result establishes a recovery defect; it does not establish the exact unavailable file on the other laptop. No private log or wallpaper path is included in the release.

Microsoft documents that [GetMonitorDevicePathCount](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nf-shobjidl_core-idesktopwallpaper-getmonitordevicepathcount) includes disconnected displays, and [GetMonitorRECT](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nf-shobjidl_core-idesktopwallpaper-getmonitorrect) returns S_FALSE for them. Backing up every enumerated assignment could block a laptop because an old external display references a removed image. New capture/apply targets connected displays only; detached assignments are not changed or interpreted as an outside wallpaper choice. Legacy queryable detached assignments already using jellyflower remain restorable from their prior record.

If a connected source cannot be read, [GetWallpaper(NULL)](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nf-shobjidl_core-idesktopwallpaper-getwallpaper) must return S_OK with that exact common source before the [SPI_GETDESKWALLPAPER](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-systemparametersinfow) path may be considered. It must be different and readable. This is a guarded fallback, not a guarantee that every Windows configuration exposes a second usable copy. A mixed/slideshow S_FALSE, different source, unreadable copy or missing active source without a safe copy stops before changing Windows. JPEG/PNG/BMP signatures preserve a usable backup extension. Files are copied byte-for-byte, and native read errors are retained. On restoration an unreadable original no longer prevents using an existing readable backup. Private Spotlight/slideshow provider settings remain untouched.

[RPC_S_SERVER_UNAVAILABLE](https://learn.microsoft.com/en-us/windows/win32/debug/system-error-codes--1700-3999-) and the relevant disconnected/server-died COM results discard the cached proxy. Capture/backup repeats at most once with a new COM instance. Apply/restore failures release the stale proxy for rollback or the next request, but do not blindly replay partially completed setters. Repeated server unavailability remains an error, without a reconnect loop or polling timer. The sleeping wallpaper worker and persisted recovery rules remain. UI errors are lowercase and fit the inherited Windows font at each tested DPI; unknown failures expose a hexadecimal HRESULT inline. Controller diagnostics add wallpaperStatus and wallpaperLastResult without changing helper shared layouts.

## Taskbar and independent wallpaper theme controls (0.17.0)

The controller uses [ABM_GETTASKBARPOS](https://learn.microsoft.com/en-us/windows/win32/shell/abm-gettaskbarpos) to identify the native system taskbar edge and [ABM_GETSTATE](https://learn.microsoft.com/en-us/windows/win32/shell/abm-getstate) for auto hide. Unsupported, unknown and non-bottom edges disable the row. Every explicit toggle rechecks the edge, retains other state flags and calls [ABM_SETSTATE](https://learn.microsoft.com/en-us/windows/win32/shell/abm-setstate) with the Shell_TrayWnd handle. That API always returns TRUE, so the code reads the resulting state instead of treating the return value as success. This is Windows' persistent preference, with no private registry-layout patch, Explorer restart or app-owned override on startup/exit. Third-party taskbar replacements that do not implement these native appbar contracts are unsupported.

Wallpaper auto reuses AutoTheme's location and SolarSchedule implementation with separate registry values and a separate controller completion message. It never calls SetWindowsLightTheme. The selection is persisted independently of location availability; system is the upgrade/default mode. While auto has no usable permission/location, WallpaperUsesLight falls back to the current Windows preference. New consent is requested only on a menu action while the wallpaper is enabled. Startup revalidates a previously approved location without prompting. The rounded local location cache is scoped independently of Windows-theme auto. Disabling wallpaper destroys its watcher and cancels its window timer; selecting auto while off performs no geolocation work. Approved cache data may remain until a later selection/permission change.

The daily cached sunrise/sunset schedule, non-waking one-shot deadlines, clock/resume invalidation and bounded daily location refresh use the existing implementation. The controller only queues a wallpaper worker refresh when the selected light/dark decision changes or an outside display/desktop event explicitly requires inspection. Worker completion messages never queue an identical request, preventing a feedback loop. Both settings can be automatic independently. The new UI and preferences live in the controller only; no injected helper protocol/generation changes.

## Bounded location ownership (0.17.1)

0.17.0 requested coordinates only at activation/startup and daily refresh, but retained the Geolocator and a StatusChanged listener throughout automatic mode. A one-time request is not the same as PositionChanged tracking; the old design nevertheless left a location-service object/listener alive unnecessarily. 0.17.1 removes both persistent members and both location/status subscriptions. Microsoft recommends [one-time location requests](https://learn.microsoft.com/en-us/windows/uwp/maps-and-location/guidelines-and-checklist-for-detecting-location) when continuous updates are unnecessary; [GetGeopositionAsync](https://learn.microsoft.com/en-us/uwp/api/windows.devices.geolocation.geolocator.getgeopositionasync?view=winrt-26100) provides that operation.

The locator exists only inside the acquisition coroutine, using city-level accuracy, up-to-one-hour cached Windows fixes and a 15-second timeout. State retains IAsyncInfo only while consent/acquisition is pending so Disable/destruction can request cancellation outside the state lock. Generation checks prevent cancelled/stale completions from saving coordinates or restarting auto. The completed handle is cleared before notification and all locator/result references are scoped out. Cached rounded coordinates and SolarSchedule remain; regular events need no location object. Normal refresh stays daily and transient errors may retry after 15 minutes. No sensor-use or permission polling loop is added.

Removing the status watcher means permission revocation is detected by the next bounded acquisition, rather than immediately. Cached solar decisions may continue until then; a denied refresh clears the corresponding automatic flag/cache. The app never writes the Windows global location-services setting or revokes other apps' permission. A retained Windows permission grant is distinct from an active location reading, and Windows/provider location-indicator timing is not controlled by jellyflower. LocationLifetime exercises the actual production coroutine with a fake provider/async operations to count objects, cancellation and stale writes without reading a real location.
